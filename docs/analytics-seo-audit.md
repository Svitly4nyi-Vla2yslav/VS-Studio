# Analytics, SEO and i18n audit

Audit date: 2026-10-18. Branch: `feature/analytics-seo-conversions`.

## Initial state

- React 19, TypeScript, Vite 6 and React Router 7 SPA with build-time per-route HTML generation.
- Firebase Analytics was initialized through `src/firebase.ts` without consulting the existing cookie consent state.
- Assistant events were sent through Firebase Analytics and also pushed to `dataLayer`, creating a duplicate-tracking risk.
- No standalone GTM container was configured. A direct gtag implementation is sufficient and avoids adding another runtime.
- Existing measurement configuration uses `VITE_FIREBASE_MEASUREMENT_ID`; the new module also supports the preferred `VITE_GA4_MEASUREMENT_ID` without inventing a value.
- Cookie consent stored essential/statistics/marketing choices in `cookie_consent_v2`, but did not notify analytics code when a choice changed.
- SPA navigation had no centralized `page_view` tracking.
- The main `/kontakt` form correctly waits for a successful Netlify `contact` function response, but did not emit a conversion or redirect to a thank-you page.
- The AI lead flow correctly treats a lead as successful only after `create-lead` returns success. Its previous event name was internal and not the requested `assistant_lead` conversion.
- The legacy `ContactComponents/ContactForm.tsx` targets an unrelated appliance-repair form and is not mounted by the current router.
- SEO metadata, canonical URLs, JSON-LD, sitemap, robots and route-specific static HTML are generated by `scripts/generate-seo-assets.mjs` from `src/seo/route-seo.json`.
- `/webdesign-hildesheim`, `/seo-hildesheim`, and `/websites-fuer-handwerker` already had one H1, structured H2 content, contact CTAs and canonical URLs.
- The global `/* /index.html 200` fallback returned a successful homepage shell for unknown URLs, creating soft 404 responses.
- `robots.txt` allowed all crawlers implicitly but did not document the independent OpenAI search/training crawler choices.
- All 13 locale JSON files are valid JSON and contain `home.projects.title`, `home.projects.items.handwerk.description`, and `footer.impressum`.
- i18next used an HTTP backend and German fallback, but React rendering was not explicitly delayed until initial translations finished. Locale assets had no dedicated cache header.

## Implemented architecture

- `src/analytics/analytics.ts` is the only GA4 gateway. It loads gtag once, only after statistics consent, only on the production hostname, and disables automatic page views.
- Preview, localhost and test environments never send production analytics. `VITE_GA4_DEBUG=true` enables GA4 debug mode on an authorized production-like host.
- The controller tracks deduplicated SPA `page_view` events and delegated `tel:`, `mailto:` and WhatsApp clicks.
- UTM values are allowlisted, length-limited, held in memory before consent and persisted only to session storage after statistics consent.
- Conversion events carry only operational metadata such as `lead_source`, `form_id`, `page_location`, language, and a random event ID. Names, emails, phones and message content are excluded.
- `/danke` is prerendered and `noindex`, and direct visits or refreshes never create a conversion. The conversion is emitted immediately after the confirmed server response, before navigation.
- Known routes use their generated static HTML; the final Netlify fallback now returns `404.html` with status 404 instead of a soft 404.

## Manual platform configuration

1. In Netlify, add `VITE_GA4_MEASUREMENT_ID` with the existing GA4 web stream ID. The legacy `VITE_FIREBASE_MEASUREMENT_ID` remains a fallback during migration.
2. In GA4 Admin, mark `generate_lead` and `assistant_lead` as key events if they should count as conversions.
3. Register useful custom dimensions only if reporting needs them: `lead_source` and `form_id`. Do not register PII.
4. Use DebugView only from an explicitly configured test hostname; localhost intentionally does not send to production GA4.
5. Submit `https://vs-web-studio.de/sitemap.xml` in Google Search Console and inspect the three priority local pages after deployment.
6. Verify Netlify/CDN/WAF logs do not return 403 or challenges to `OAI-SearchBot`. `GPTBot` is independently allowed in the current policy and can be changed without affecting ChatGPT Search eligibility.

## Known limits

- Search Console query priorities were supplied in the task; no authenticated Search Console export was available in the repository.
- A local build can validate prerendered output, but production HTTP status, WAF behavior, GA4 DebugView, Search Console indexing and real-user INP require post-deploy checks.
- Existing malformed-looking characters in some non-German locale content are pre-existing data-quality issues and were not bulk rewritten without approved translations.

- `npm run check`: passed (ESLint, TypeScript, Vite production build and SEO generation).
- `npm run validate:analytics-seo`: passed for all 13 locale dictionaries and the conversion/SEO invariants.
- Direct HTTP requests returned 200 with unique prerendered titles for home, contact, thank-you and all three priority local SEO pages.
- Lighthouse 12.8.2 Mobile: Performance 35, Accessibility 100, Best Practices 96, SEO 100, LCP 7.9 s, CLS 0, TBT 1.85 s, main-thread work 8.4 s, unused JavaScript estimate 92 KiB, transfer 2,596 KiB.
- Lighthouse 12.8.2 Desktop: Performance 67, Accessibility 97 before the accessible-name correction, Best Practices 96, SEO 100, LCP 2.0 s, CLS 0.027, TBT 430 ms. The corrected Mobile rerun restored Accessibility to 100; a second Desktop run was not needed for that viewport-independent markup fix.

- Browser UI automation was unavailable in the execution environment, so no visual click-through or console-panel E2E result is claimed.
